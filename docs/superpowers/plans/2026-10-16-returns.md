# Returns (T2) Implementation Plan

> **For agentic workers:** implement task by task with TDD (superpowers:executing-plans). Steps use `- [ ]`.

**Goal:** customers request returns of completed orders; store staff receive them, then refund (T2: restock +
refund + status in one transaction) or reject them.

**Architecture:** rules in `sql/` (constraints, two triggers, one view); one service module
`app/services/returns.py` (one call = one transaction), thin router `app/routers/returns.py`, schemas
`app/schemas/returns.py`; web pages in their own files, existing pages get one line each.

**Tech Stack:** PostgreSQL 18, psycopg2, FastAPI, pytest; Next.js 16, openapi-typescript, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-16-returns-design.md`

## Review Focus

- The same key sent again with a *different* body replays the first return unchanged (no fingerprint) → Task 2
  `test_a_replay_with_a_different_body_returns_the_first_return`.
- A blank reason (`"   "`) on a request or a rejection → 422, not a row → Task 2/3
  `test_a_blank_reason_is_a_validation_error`.
- The same line twice in one request → 409 `return_line_pk`, nothing saved → Task 2
  `test_the_same_line_twice_is_refused_and_saves_nothing`.
- The form's cap ignores rejected returns (their units can be asked for again) → Task 5 unit test
  `returnable_ignores_rejected_returns`.
- A lost answer retried from the form reuses its key; an edited form gets a new one → Task 5 unit tests.
